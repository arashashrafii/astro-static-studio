# Issue #22 — Collection-to-theme mapping PoC

## Result

The isolated prototype shows that two preset sections can read the same validated
Collection and item objects, derive different card view models, and reflect a single
edit in both views without copying or mutating canonical records. A versioned PoC
envelope also carries the prototype settings through a real content backup/restore
round-trip.

This is a contract experiment only. It does not change the editor, site renderer, or
the production backup format.

## Evidence

`tests/collection-mapping-poc.test.ts` exercises three cases:

1. Base fields (`title`, cover image, derived description) and an optional Category
   field map into `featured-grid` and `compact-list` sections. Both outputs retain the
   same item ID and source object. Editing the source title once updates both outputs.
2. Unknown Category fields are rejected by the mapper. The Content V2 schema rejects
   an invalid Collection reference and an unsupported block type.
3. A versioned PoC envelope containing a real Studio backup plus separate theme
   settings restores canonical content and preserves both mappings.

Focused verification on the `main` baseline at `45c03ef3037a8416f2b465f9307b11655ea21a6f`:

```text
node --test --import tsx tests/collection-mapping-poc.test.ts
3 passed, 0 failed
```

## Current implementation limits observed

- Content V2 already keeps item data canonical and allows multiple page blocks to
  reference one Collection. The Atelier renderer turns that Collection into its
  current list and detail views.
- The renderer currently ignores the page block's `view`, `sort`, and `limit` fields;
  a second section with a different preset needs an explicit adapter/rendering path.
- The existing backup stores canonical content and media only. The tested envelope is
  a prototype wrapper and is not read or written by the application backup API.
- The prototype identifies a placement by page ID plus block index. Reordering blocks
  can silently point that mapping at a different block, so this key is not suitable for
  persisted production settings.
- Repeated Collection renderer instances also need instance-scoped DOM IDs and controls;
  the current renderer uses a fixed ID and global selectors.

## Proposed contract for owner decision

1. Give each generic page block a stable `placementId` (created when the block is added,
   preserved on edit, and generated by a versioned migration for existing V2 content).
   This identifies placement without making the ID theme-specific.
2. Keep a versioned `ThemeSettingsV1` separate from Content V2. A mapping references
   `themeId`, `placementId`, a supported theme section/display preset, and optional
   field IDs from the referenced Collection. Records remain the only source of item
   content.
3. Include these settings in a versioned portable backup envelope beside the existing
   site backup. Continue restoring existing backup format v1 with default/empty theme
   settings; validate all setting references before committing a restore.
4. Render each placement through the selected theme adapter. Generate unique DOM IDs
   per placement and reject unknown fields, unsupported block types, and broken
   references before rendering.

This proposal adds a generic placement identifier and changes the backup contract, so
it requires explicit owner approval before product integration. The PoC's block-index
key and envelope must not be treated as the approved production schema.

## Not included

No main-editor controls, theme registry, production adapter, production backup migration,
or customer content migration is included. Those changes should follow the approved
contract in focused implementation issues.
