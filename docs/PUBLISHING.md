# First publishing provider decision

**Status (2026-10-26): Cloudflare Pages Direct Upload is implemented. The full sample-site QA preview upload completed, deployment metadata matched the selected project/branch, and the owner confirmed the preview became accessible. The agent did not independently verify final public reachability from its restricted environment. Production publishing remains untested. See [M2_VALIDATION](M2_VALIDATION.md).**

## Decision

Use **Cloudflare Pages Direct Upload through Wrangler** for the first publishing adapter. It matches Studio's local build model: Studio produces static assets locally, and Wrangler can upload a prebuilt directory directly from the owner's computer. Direct Upload cannot later be switched to Git integration; moving to Git integration requires a new Pages project and domain/configuration migration. The owner approved this tradeoff for M2.

A disposable Cloudflare QA project was created and a preview deployment completed during validation; do not mistake it for a production release. Studio defaults to a preview deployment and requires a separate in-product confirmation before publishing to production.

## Implemented flow

1. Studio saves pending content and builds the site locally. If the build fails, it keeps the last good build.
2. On first connection, Wrangler opens Cloudflare OAuth and is forced to use operating-system keyring storage for every command. If the keyring is unavailable, authentication fails instead of storing credentials in plaintext.
3. When OAuth finds one Cloudflare account, Studio selects it automatically; with multiple accounts, the owner chooses one. The owner can then choose an existing Pages project or explicitly create a Direct Upload project. Existing projects are shown only when Wrangler reports a successful production deployment whose branch can be verified. A newly created project is kept in the list before its first deployment. Studio stores the account id, project name and production branch in ignored local configuration until the owner selects another account or project, or disconnects. Project creation and uploads pass Wrangler's `--force` option so agent-aware Pages-to-Workers delegation cannot change the approved Direct Upload destination.
4. The dashboard saves pending edits, builds the Astro site locally, then validates and uploads that exact static output. Preview uses the `studio-preview` branch, which Studio refuses when it matches the project's production branch. Production upload targets the recorded production branch and requires a separate confirmation. Studio verifies Wrangler's deployment metadata, then checks the resulting HTTPS site for up to 60 seconds, retrying every 10 seconds for temporary network failures and HTTP 404, 408, 429, and 5xx responses. If the exact deployment is present but its public URL cannot be reached from the runner, Studio keeps and shows the URL with an explicit “readiness unconfirmed” status; it never labels that result verified. Failed builds and uploads leave the prior local output available.
5. The owner can disconnect through Wrangler logout, which revokes OAuth access and removes stored Wrangler credentials.

Wrangler runs as a child process in a temporary empty working directory with argument arrays, never shell interpolation. The runner ignores inherited Cloudflare token/key/email (including Wrangler's deprecated `CF_*` aliases) and config overrides, passes the selected account id explicitly, enforces OS keyring storage, disables metrics, and bounds command execution. Before finalization, Studio retrieves the current OAuth token through Wrangler's supported `auth token --json` command in the API process, then uses the documented Pages upload-token, check-missing, upload, and upsert-hashes API endpoints. OAuth and the short-lived upload JWT stay in memory and never enter the browser, configuration, logs, or error messages. Assets use the same BLAKE3 identity formula as the pinned Wrangler 4.149.0 release; a known-hash test guards compatibility. Missing hashes upload sequentially in batches capped at 512 KiB of raw files and 2,000 entries (a single larger valid asset is sent alone), with duplicate content hashes uploaded once. Each successfully uploaded batch is immediately registered with `upsert-hashes`, allowing a retry to skip completed batches; a failed or uncertain batch is never registered. Safe API-process progress logs include only batch counts, file counts, encoded bytes, and elapsed time. Requests have a 30-second deadline (120 seconds for an asset batch), bounded retries, and a twenty-minute budget after OAuth retrieval covering local hashing and the preupload API sequence. If any batch fails, Studio does not ask Wrangler to create a deployment. Wrangler then performs its existing Pages deployment finalization and Studio verifies the exact deployment id, account/project, environment, branch, successful status, Pages host, and final redirect before reporting the URL. Other commands use a one-minute limit, except login. A timed-out upload is reported as unverified and the dashboard asks the owner to check Cloudflare before retrying. OAuth requests only the supported `account:read` and `pages:write` scopes. Raw CLI output is never returned to the dashboard or included in errors. The dashboard receives parsed login/account status, verified project metadata, safe errors, and a checked public URL.

For each deploy, Wrangler writes structured output to a private file in its temporary directory. Studio matches that deployment id against the deployment list and verifies the account/project, environment, branch, successful status, Pages host, and final redirect before reporting the URL. This prevents an older successful deployment from masking a newer failed one.

The upload boundary is the small `StaticUploadProvider` interface in `apps/api/src/publishing.ts`. It receives only a validated static directory. A verified deployment returns its URL only after the health check succeeds; a deployment whose exact metadata is verified but whose URL remains unreachable returns the URL with `verified: false` and a safe status message. This leaves room for a future Arvan S3 adapter without changing the Astro build; Arvan is not part of M2.

## Constraints and remaining validation

- Cloudflare Pages Direct Upload supports prebuilt assets via Wrangler. Current documented limits are 20,000 files and 25 MiB per file; Studio checks both before upload and rejects symlinks, `_worker.js`, `functions/`, and `.env` files.
- The full Sara sample's 259 unique asset hashes uploaded and were registered in the isolated QA Pages project, and Wrangler's resulting preview deployment metadata matched that project and branch. This runner could not reach either the exact deployment host or the QA project's base `pages.dev` host: IPv4 HTTPS connections timed out and IPv6 was unreachable. Public readiness therefore remains unconfirmed from this environment, and production publishing has not been exercised.
- The installed Wrangler 4.149.0 CLI was checked locally. Its help confirms `whoami --json`, Pages project/deployment list JSON, `pages deploy --no-bundle` (deploy has no `--json` flag), `pages project create <project-name> --production-branch <branch>`, and login `--scopes`/`--use-keyring`. In agent sessions, Wrangler may delegate Pages creation and uploads to Workers; `--force` opts out so Studio stays on the approved Pages Direct Upload path. Creation reports success as human-readable output after the remote API call. Its scope list confirms `account:read` and `pages:write`; `pages:read` is not an available scope. Source and CLI output confirm the Pascal-case JSON fields Studio parses.
- The static asset hash format follows the installed, pinned Wrangler 4.149.0 implementation: BLAKE3 of the base64-encoded bytes followed by the file extension, truncated to 32 hexadecimal characters. A fixed test vector guards against dependency or CLI upgrades that change this compatibility contract.
- Wrangler project-list JSON omits the production branch. Studio derives it from the latest successful production deployment; projects without one are omitted unless the owner just created and selected the project, whose configured `main` branch is retained locally until its first deployment.
- Direct Upload does not use Cloudflare's Git-connected automatic-build workflow. Studio remains the local build source.
- Cloudflare recommends considering Workers for some new projects; Pages remains the selected host for this proof because it serves Studio's static output directly.
